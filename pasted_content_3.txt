# PROMPT MESTRE — AMPLIAÇÃO MÁXIMA DO DUCK

## MISSÃO PRINCIPAL

Você está trabalhando sobre um projeto EXISTENTE chamado:

**DUCK — Beats, Produção e Portal de Clientes**

Não reinicie o projeto.

Não substitua arbitrariamente o que já funciona.

Não crie uma demonstração fictícia.

Não transforme a aplicação em um conjunto de telas bonitas sem funcionamento real.

Sua missão é transformar o projeto existente em uma **plataforma digital operacional, modular, auditável, comercializável, extensível e progressivamente autônoma**, preservando o legado funcional já construído.

A prioridade é:

**FUNCIONAMENTO REAL > ARQUITETURA SÓLIDA > AUTOMAÇÃO > SEGURANÇA > AUDITORIA > EXPERIÊNCIA > ESTÉTICA**

Tudo aquilo que não contribua para esses objetivos deve ser removido, simplificado ou colocado em segundo plano.

# 2. AUDITORIA MASSIVA

Faça uma auditoria em múltiplas camadas.

## Auditoria de código

Verifique:

* bugs;
* dead code;
* código duplicado;
* componentes órfãos;
* imports desnecessários;
* dependências desnecessárias;
* problemas de tipagem;
* tratamento incorreto de erros;
* estados inconsistentes;
* race conditions;
* problemas assíncronos;
* memory leaks;
* problemas de cache;
* chamadas redundantes;
* endpoints inconsistentes;
* validações ausentes;
* problemas de segurança.

## Auditoria de arquitetura

Verifique se:

* frontend e backend estão adequadamente separados;
* regras de negócio estão centralizadas;
* dados críticos não dependem do frontend;
* permissões são verificadas no servidor;
* operações financeiras são idempotentes;
* webhooks podem ser reprocessados com segurança;
* jobs podem ser retomados;
* falhas não corrompem o estado;
* serviços podem ser substituídos futuramente.

## Auditoria de segurança

Verifique:

* autenticação;
* autorização;
* controle de sessão;
* exposição de secrets;
* variáveis de ambiente;
* uploads;
* downloads;
* URLs privadas;
* acesso a arquivos;
* SQL/NoSQL injection;
* XSS;
* CSRF;
* SSRF;
* abuso de endpoints;
* rate limiting;
* validação de arquivos;
* permissões administrativas;
* logs contendo informações sensíveis.

Nunca coloque secrets no frontend.

Nunca faça uma integração parecer funcional quando as credenciais reais não existem.

# 12. AUTOMAÇÕES

Construir um verdadeiro motor de automação.

**EVENTO → CONDIÇÃO → AÇÃO**

Exemplo:

→ pagamento confirmado
→ gerar pedido
→ gerar licença
→ liberar arquivos
→ enviar comunicação
→ registrar evento
→ atualizar métricas.

Outro:

Cliente iniciou checkout
→ não concluiu
→ esperar período configurável
→ verificar novamente
→ executar ação autorizada.

Não criar spam.

Todas as automações comerciais devem ser configuráveis e desativáveis.

MANUAL

   ↓
AUTOMATIZADO
   ↓

   ↓
AUTÔNOMO COM SUPERVISÃO

Não ativar automações perigosas simplesmente para dizer que o sistema é "autônomo".

# PRINCÍPIO FINAL

O objetivo não é fazer o projeto parecer maior.

O objetivo é fazer o projeto ser **mais capaz**.

Cada ampliação deve responder a pelo menos uma destas perguntas:

**Isso vende?**

**Isso economiza trabalho?**

**Isso reduz erro?**

**Isso aumenta segurança?**

**Isso aumenta autonomia operacional?**

**Isso melhora a experiência do cliente?**

**Isso preserva o legado?**

**Isso prepara crescimento futuro?**

Se a resposta for não para todas:

**não implemente.**

Construa uma máquina digital real, modular e auditável, mas não invente capacidades que a infraestrutura atual não possui.

**Preserve o legado. Amplifique o que funciona. Automatize o que é seguro. Audite tudo. E deixe a plataforma preparada para crescer sem depender de uma única ferramenta, API ou fornecedor.**
